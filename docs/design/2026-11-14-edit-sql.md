# Edit and rerun SQL

**Status:** implemented. **ADR:** 0033. Builds on result export (`2026-11-14-result-export.md`).

## Why

An analyst trusts a number they can check. Today the SQL tab shows the agent's queries read-only;
changing a filter or adding a column means asking the model again, which costs money and may
change more than the one thing. Databricks Genie, Snowflake Cortex Analyst, and Metabase all show
the generated SQL and let a user who knows SQL edit and run it.

## Goals and non-goals

- Edit one of the agent's queries and run it on the same dataset; see the rows; download the
  whole result as CSV.
- A typo, plain text, or a forbidden statement gets a clear message near the editor and changes
  nothing. The agent's query and answer stay as they were.
- Non-goals: an SQL IDE (autocomplete, schema browser), saving edited queries, feeding edits back
  into memory, "fix with AI". People who do not know SQL keep asking in the chat.

## Approaches

| Approach | Trade-off |
|---|---|
| **A. A `query` job run by the worker in a sandbox (chosen)** | Same boundary as agent SQL and export: the API holds no runner token and runs no SQL. A few seconds of sandbox start-up per run |
| B. The API calls the Runner directly | Faster, but gives the API a runner token, which ADR 0024 and ADR 0032 keep out of it |
| C. Run DuckDB in the browser (DuckDB-WASM) | No server work, but ships the whole dataset to the browser and bypasses audit and limits |

## Design

1. **SQL tab.** Each query has **Edit**. The editor starts from the agent's SQL; **Run** sends it,
   **Reset** returns to the agent's SQL. Results show under the editor with **Download CSV**.
2. `POST /v1/runs/{run_id}/queries` with `{sql}` (at most `MAX_SQL_CHARS`). The API checks the run
   belongs to the workspace and succeeded, and the dataset is ready. It runs the SQL guard
   (`validate_select`, DuckDB dialect) **before** queuing: a parse error, a non-`SELECT`, several
   statements, or a file read is a 422 with the guard's message, and no job is made. It applies
   the job rate but not the model budget (no model call), enqueues a `query` job with
   `{run_id, dataset_id, sql}`, and audits `query.create` with the SQL length, not the SQL.
3. The worker's `query` handler checks the SQL again, runs `Runner.query` (50 rows, 15 s, the
   locked DuckDB engine) and completes with `{sql, columns, rows, truncated}`. A DuckDB error
   (wrong column, bad cast) fails the job with DuckDB's message, which names the problem and often
   a candidate column. `SqlResult.error` never carries sandbox stderr. "Runner unavailable" is
   retried; time and memory limits fail with fixed messages.
4. `GET /v1/queries/{id}` returns `{id, status, sql, columns, rows, truncated, error}`.
5. `POST /v1/queries/{id}/export` exports a succeeded query job like a run's query: the export job
   names the query job, never SQL, and the same changed-dataset rule applies from the query job's
   time. File name: `da-agent-<query id prefix>-edited.csv`.

Guard messages from sqlglot carry ANSI underline codes; the guard strips them, which also cleans
what the model sees.

## Left to the builder

Editor widget (a plain textarea is enough), layout of the result under the editor.
