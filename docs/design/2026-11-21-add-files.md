# Add files to a dataset

**Status:** approved 2026-11-21. The user chose versions inside one dataset (approach A), ask on
overlap (option 3), labelled old answers (option 1), and model-proposed repairs the user approves
(option 2). **ADR:** 0045 (to write).

## Why

A user who is already chatting about a dataset finds data missing: next month's orders, or a
customer list. Today the only path is a new upload. That loses the conversation, every note and
metric in `dataset_memories` (keyed by `dataset_id`), and spends the spec proposal again. Users are
non-technical first, so the system, not the user, must work out what the new file is.

The user decided (2026-11-21):

- Both cases are in scope: a file with the **same shape** as an existing table (more rows) and a
  file with a **different shape** (a new table). The system decides which.
- Overlap with existing data is checked before anything is applied. Each new file is "add" by
  default and can be set to "replace <old file>". When overlap is found, the user chooses; rows are
  never silently added twice (option 3).
- Earlier answers in the chat stay as they are, labelled with the data version they used, after a
  divider in the chat (option 1). No automatic recompute and no new conversation.
- A same-shape file whose rows fail the existing spec's quality checks is not applied
  automatically. The model proposes a fix limited to the failing columns or rules of the existing
  table, shown as a before/after change the user approves (option 2).
- Build approach A: versions inside the same dataset, keeping the dataset id.

## Goals, non-goals, anti-goals

**Goals.**

- `POST /v1/datasets/{id}/files` adds files to a `ready` dataset and starts a new **dataset
  version**. The dataset stays `ready` on its current version the whole time; chat keeps working.
- The system classifies each raw table of the new version as unchanged, **grown** (same header as an
  existing table, rows from new files), or **new** (a header no existing table has).
- Same shape, no overlap, nothing removed, new rows pass the quality checks: the version is built with the approved spec, with no
  model call, and applied without review. The user sees a short summary.
- Overlap found: the version waits for the user's choice for each affected table: replace the old
  file, drop the overlapping new rows, or keep both.
- Different shape: the model proposes spec entries for the **new tables only**, plus relationships
  that touch them. Code keeps every existing table spec, including the user's edits, exactly. The
  user reviews and approves the new part, as at first upload.
- Every run records the dataset version it read. Conversation turns from an older version are
  marked as such in the prompt and in the UI.

**Non-goals.**

- Deleting a file without replacing it, or rolling back to an older version.
- Merging a near-match file (a column added or renamed) into an existing table. It becomes a new
  table, and the review says which existing table it resembles and which columns differ.
- Recomputing old answers on new data.
- Incremental ingest: every version ingests all of its files again.
- Adding files to a dataset that is not `ready`.

**Anti-goals.** Any of these makes the feature a failure even if it works:

- A number counted twice because a file overlapped old data and nobody was asked.
- A user's spec edits lost, or an existing table's spec changed by the model without the user
  approving that exact change.
- "Added 1,240 rows" while the new rows quietly parse to NULL or move to `_excluded`.
- A run that reads half-installed data, or whose dataset changes under it mid-run.
- An earlier answer that silently changes when re-run, exported, or replayed.

## Constraints

- Uploaded bytes are parsed only in the sandbox (ADR 0009). The new endpoint has the same limits as
  `POST /datasets`: file count (counted over all files of the new version), bytes, names
  (`storage_name`), and the workspace's job, rate, and money limits.
- Only the Runner starts containers. `Runner._child` accepts only a direct child of its root, so a
  version's directories are siblings named `<dataset id>-v<n>`, which `dataset_id`'s pattern
  already allows. The Runner does not change.
- `DatasetSpec` stays declarative data. A new spec field must compile to quoted SQL as the others do.
- Nothing is dropped silently (ADR 0010): rows dropped as overlap go to `_excluded` with a reason.
- Core code has no DataMate-specific logic. The eval builds datasets with `prepare_dataset` and is
  not affected.
- The UI is in English (progress.md: users non-technical first, UI in English).

## Approaches

| | Approach | Trade-off |
|---|---|---|
| **A (chosen)** | Versions inside one dataset: `dataset_versions` table, one build directory per version, runs record their version | Ids, URLs, conversation, and memory stay. Reuses header grouping and `rebuild_dataset`. Data version fits the harness work (manifest, replay, time travel). Costs a migration and a full re-ingest per version |
| B | A child dataset per update, conversation and memory moved to it on apply | Lifecycle almost unchanged, but ids change: memory foreign keys, URLs, old runs, and a list of hidden datasets all need handling |
| C | Ingest only new files and UNION them with the old build in views | Fastest for large data, but `fill_down`, `dedupe`, and exclusion rules work per table and would differ; the overlap check needs the old data anyway; two mounts |

The user chose A because it keeps the conversation and reuses the most existing code.

## Design

### Data model (migration 0017)

`dataset_versions`:

| Column | Meaning |
|---|---|
| `dataset_id`, `version` | Primary key; `version` starts at 1 |
| `status` | `uploaded` → `checking` → (`applied` \| `needs_choice` \| `proposed` \| `failed` \| `discarded`); `needs_choice` and `proposed` lead to `building` → `applied` |
| `files` | The version's file list: kept files from the previous version plus new ones, each with `name`, `stored_as`, `bytes`, `added_in` (version), and `replaces` when set |
| `spec`, `summary`, `documents` | As on `datasets`, for this version |
| `changes` | What the check found: per table `unchanged`/`grown`/`new`/`removed`, rows added, overlap counts with examples, near-match notes |
| `choices` | The user's overlap choices per table |
| `error` | Readable reason when `failed` |

`datasets` gains `current_version` (the applied version runs read). The migration creates version 1
for every existing dataset from its current row, with build directory `<id>` (the existing
directory, so nothing moves) and upload folder `<id>`. Later versions use `<id>-v<n>` for both.
`dataset_versions` holds the directory names, so the opener never guesses.

`jobs` gets a new kind, `version`, for the check-and-build work.

At most one version per dataset may be open (not `applied`, `failed`, or `discarded`). A second
upload while one is open returns 409.

### Flow

1. **Upload.** `POST /v1/datasets/{id}/files` with files and, per file, `replaces` (an existing
   stored name) or nothing. The API checks the dataset is `ready` and in the caller's workspace,
   creates upload folder `<id>-v<n>` with the kept files linked from the previous version's folder
   (hard links, copy as a fallback) and the new files saved, inserts the version row as `uploaded`,
   and enqueues a `version` job, all in one transaction. Returns 202 with the version number.
2. **Check** (worker, `version` job, status `checking`). Ingest the version's folder in the sandbox.
   Match each raw table to the previous version's tables **by header**, not by raw table name:
   raw table names come from the first file in sorted order, so a new file that sorts first renames
   the group. Rewrite the spec's `source` fields to the new raw names. Classify tables as
   unchanged, grown, new, or removed.
3. **Build with the current spec** (no model). New raw tables are built as text by
   `_with_missing_tables` for now. The version build does not switch on `dedupe` by itself
   (`_with_dedupe` is not called), since that would change an approved spec without asking. The
   build report gains, for each grown table, **overlap checks** between rows from files new in
   this version and rows from earlier files (`_source` and the version's `added_in` tell them
   apart; files new in the same upload are also checked against each other, in upload order). The
   checks run on rows **before** any dedupe:
   - exact: every clean column equal. On a table whose approved spec already has
     `dedupe: exact`, these rows are reported as "removed by the existing duplicate rule", not
     asked about; key and date overlaps on that table are still asked about.
   - key: equal values in key columns. `_identifier_columns` misses most order files (numeric ids,
     ids repeated across line items), so key detection is widened for this check: numeric ids are
     allowed, and a key may be two columns (such as order id plus line or product) when together
     they are at least 99% distinct in the old data. Detection runs on every grown table, not only
     on tables with `exclude_rows`.
   - date range: for a table with a date column, new rows whose dates fall inside the old data's
     date range. This catches a re-export where a field such as status changed, which neither
     check above sees. It can be a false alarm (late orders for a past month); that costs one
     question, never a silent drop.
   Each finding comes with a count and up to 5 example rows.
4. **Decide** (code, not the model):
   - **Quality check** on every grown table, on the rows from new files, with the thresholds of
     first ingestion (`parse_problems`, ADR 0010): a column's parse rate under 98%, or an
     existing `exclude_rows` rule that removes more than 10% of the new rows or rows that look
     like records. A failure leads to a repair proposal (step 5b) and status `proposed`.
   - No new tables, no removed tables or columns, no overlap, no quality failure: install the
     build as `<id>-v<n>`, then, in one transaction, mark the version `applied` and set
     `current_version`.
   - Overlap: status `needs_choice`.
   - New tables: propose their spec (step 5), then status `proposed`. When there is also overlap,
     the user answers both on one review screen.
   - A table or column removed (a replaced file was its only source): status `proposed`, so the
     user confirms the loss; the review lists metrics that would turn stale.
5. **Propose for new tables.** A variant of `propose_spec` receives the profile of the new raw
   tables only, the existing spec as read-only context (table names, columns, relationships), and
   the documents. It returns table specs and relationships. Code merges: existing table specs are
   copied from the current version unchanged; from the model it keeps only table specs whose
   `source` is a new raw table and relationships with at least one end in a new table. The merged
   spec is validated by building it, with the same repair loop (3 attempts) and parse-rate checks.
   Its cost is charged to the job's run id and to the workspace budget, like ingestion.

   **5b. Repair an existing table.** When the quality check fails, the model receives the
   failing columns' profile on the new rows (patterns, sample values), the failing rules with
   rows they removed, and the existing table spec as context. It may return changes only to the
   failing columns' `type`, `date_formats`, and `true_values`, and to the failing
   `exclude_rows` rules. Code rejects any other change, keeps the rest of the table spec as it
   is, validates by building, and repairs up to 3 times as at ingestion. The result is stored as
   a per-table diff (field, before, after), not a new spec. If the model cannot fix it, the
   review shows the problem with "apply anyway" and "discard".
6. **Choose and approve.** `POST /v1/datasets/{id}/versions/{n}/approve` with overlap choices and,
   optionally, an edited spec for the new tables. Choices per table:
   - `replace`: the overlapping old file is removed from the version's file list (the user picks
     which when it is not obvious from the overlap examples);
   - `drop_overlap`: a new declarative `TableSpec` field lists explicit file pairs: rows of
     stored file B whose key (or whole row, for a table with no key) already exists in stored
     file A are excluded, reason "already in <A>". It names files, not an order, so it is a rule
     about those files only: a later version that brings another overlapping file asks again;
     nothing is dropped by a standing policy;
   - `keep_both`.
   Any change to the file list or spec queues a build (`building`); when it succeeds, install and
   apply as in step 4. `POST .../discard` drops an open version and its directories.
7. **Runs.** `create_run` puts `dataset_version` (the dataset's `current_version`) in the payload,
   next to `memory_ids`, so a resumed run reads the same version. The opener opens that version's
   build directory. Edited-SQL query jobs (ADR 0033) and exports run on the version of the run
   they come from, so an old answer re-run or exported gives the old numbers.
8. **Conversation.** `ConversationStore.recent_turns` adds to each turn from an older version a
   line such as "(answered on data version 1; the data has changed since; do not reuse its
   numbers)". The UI shows a divider where the version changed ("Added orders_dec.xlsx. Answers
   below use data version 2.") and a "data v1" badge on older answers.

### Retention

Applied versions' build directories are kept, so old answers can be re-run and exported. A dataset
may have at most `DA_AGENT_MAX_DATASET_VERSIONS` versions (default 20); past that the upload
returns 409. Failed and discarded versions' directories are removed at once. Dataset deletion
does not exist today and is not part of this work; when it is built, it removes every version.

Stored upload files are immutable once saved: only the upload endpoints write to the uploads
folder, and they write new files only. Hard links between version folders rely on this.

### UI

- In the chat, an **Add files** button next to the composer opens a dialog: drop files, and for each
  choose **Add** (default) or **Replace** with a list of the dataset's files.
- While a version is open, a status card sits at the end of the chat: "Checking new files…", then:
  - applied: "Added 1,240 rows to orders (parse rate 99.9%)" and the divider;
  - needs a choice or a review: a card that opens the review screen: overlap per table with
    examples and the three choices, new tables in the existing spec editor (only the new tables
    editable), proposed repairs to existing tables as before/after rows with the parse rate
    each gives (accept or reject each), removed tables and stale metrics;
  - failed: the reason, and a button to dismiss.
- Asking questions stays possible throughout; they run on the current version.
- The dataset page lists versions with their files and status.

### Failure handling

- Ingest, build, or proposal fails: version `failed` with a readable reason; the current version is
  untouched. The job completes, as ADR 0019 does for datasets.
- Worker dies mid-job: the job is retried (leases, ADR 0017). Each step writes to fresh staging
  directories; install renames into `<id>-v<n>` only after a good build, and applying is one
  transaction, so a retry never leaves a half-applied version.
- A user's model budget is exhausted during the proposal: `failed` with the budget message; the
  same-shape path needs no model and is not affected.

### Security

- Same upload checks as `POST /datasets`; files parsed only in the sandbox.
- Workspace check on every new endpoint; the opener checks the version belongs to the dataset.
- Audit events: `dataset.files_add`, `dataset.version_approve`, `dataset.version_discard`.
- Threat model: add the new endpoint to the path traversal and upload rows.

### Observability

- Spans for the version job's steps (ingest, match, build, propose, install) and its model calls,
  as for ingestion today.
- Run events and `GET /v1/datasets/{id}` show the open version's status for the UI to poll.
- Run results and the run list show `dataset_version`.

## Testing

- Unit: header matching when a new file renames the raw group; classification; spec merge keeps
  existing tables byte for byte and drops model output for existing tables; a repair diff that
  touches a non-failing column or field is rejected; a rejected repair leaves the spec unchanged; overlap counts (exact,
  key, no key); `drop_overlap` compiles to quoted SQL and fills `_excluded`.
- Lifecycle with the fake Runner and a fake LLM: same shape applies without a model call; overlap
  waits; a same-shape file with a new date format waits with a repair proposal; new table proposes; a removed table needs approval; a second open version is refused; a
  failure leaves the current version serving; a retried job does not apply twice.
- API: workspace isolation, 409 on a non-ready dataset, file limits over the whole version, a run
  records its version, an old run's query job and export read the old version.
- Sandbox: the Runner opens `<id>-v<n>` and still refuses paths outside the root.
- No eval run is needed: the agent graph and prompts do not change except the conversation turn
  label. One real-model check of the new-table proposal on a demo dataset costs cents; ask first.

## Left to the builder

- Exact endpoint shapes, payload field names, and where the overlap code lives in `build.py`.
- How hard links fall back to copies across volumes.
- The wording of UI text and the turn label, within the meaning above.
- Whether the version job is one job or a check job plus a build job, as long as steps are
  idempotent and the apply is one transaction.

## Calls made by Claude, not the user

- "Same shape" means the same raw header after the existing column-name normalisation; near
  matches become new tables.
- Overlap is found three ways (exact row, widened key, date range), before dedupe; key detection
  is widened beyond `_identifier_columns` (numeric ids, two-column keys).
- `drop_overlap` names file pairs; it is never a standing policy, so each new overlap is asked.
- A version build never switches on `dedupe` by itself.
- Dataset deletion stays out of scope.
- Quality thresholds for new rows are those of first ingestion; a repair may touch only `type`,
  `date_formats`, `true_values` of failing columns and the failing `exclude_rows` rules.
- Any version that removes a table or column needs approval, even with no new tables.
- One open version per dataset; at most 20 versions; applied builds kept for re-runs and exports.
- Version 1 of existing datasets keeps its current directories; later versions use `<id>-v<n>`.
